# PcTime 客户端

Windows 桌面端的屏幕使用时间统计程序。采集本机每个应用的前台使用时长，存进本地
SQLite，按需导出 CSV，并把「应用名 + 使用时长」上传到[自建服务端](../server/README.md)
用来生成报告邮件。

当前打包程序名为 `PcTime.exe`。**不依赖服务端也能完整工作** —— 只有「上传数据」和
「保存订阅」这两件事需要联网，其余功能全部本地闭环。

> 仓库总览、隐私声明、License 在[根 README](../README.md)。

本组件保留 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md` 和 `licenses/`，便于单独
分发。来源包括 DABIAN-afk/usagetime 的客户端基础与 Planshit/Tai 的网站统计设计。
客户端打包会收集实际依赖的许可文本，浏览器扩展可用
`python tools/package_extension.py` 独立打包。上游许可记录与二进制发行待确认项见
本目录的 `THIRD_PARTY_NOTICES.md`。

## 独立运行与可选上传

只部署 `client/` 即可；本地采集、SQLite、排行、时间线、导出与浏览器插件连接均
不导入服务端代码，也不需要 MySQL。服务器未启动或断网时继续记录，上传失败后保留
本地数据，下次联网自动补传；设置中关闭自动上传即可作为纯本地统计工具使用。
邮件由服务器发送，客户端无需常驻服务端，服务端也不反向连接客户端。

连接配置与服务端部署见 [部署说明](../server/deploy/README.md)。普通应用汇总支持
HTTP，网站/时间线远程上传需要 HTTPS。仅验证同步逻辑时，可用
`python client/tools/verify_sync.py --url http://127.0.0.1:8000`；此命令仅用于临时
测试服务器，会写入合成数据，使用临时 SQLite，不修改真实本地记录。

## 功能特性

- **实时监控** — 每秒检测前台窗口，精确记录应用使用时长
- **智能休眠** — 自动检测无操作状态，停止计时避免空挂误计
- **今日统计** — 24 小时柱状图，直观展示每小时使用分布
- **本周统计** — 7 天柱状图，一目了然每周使用趋势
- **应用排行** — 按使用时长排序，支持自定义应用名称映射
- **多进程合并** — 自动把同一软件的主进程与辅助进程合并统计，避免重复显示
- **准确图标** — 优先从实际使用的程序文件提取图标，并兼容桌面/开始菜单快捷方式
- **防止重复计时** — 只允许一个统计实例运行，误点多次也不会重复记录
- **系统托盘** — 最小化到托盘后台运行，左键点击打开面板
- **暂停/恢复** — 临时停止统计，自由控制
- **忽略列表** — 排除不需要统计的应用
- **开机自启** — 一键设置开机自动启动
- **自动导出** — 每天/每周/每月把使用时间写成 CSV，按「年/月/日」存到 `client/data/`
  目录（见[自动导出](#自动导出)）
- **每日上传** — 每天把使用记录传给自建服务端（FastAPI + MySQL），用于生成报告邮件；
  可在设置页一键关闭，关掉后程序不会发出任何网络请求（见[数据上传](#数据上传)）
- **每日 / 每周报告邮件** — 在「设置 → 数据上传」里填邮箱订阅。服务端每天 00:03
  发送昨天的完整报告（平日是日报，报告日为周日时换成整周周报），细节见
  [服务端 README 的「邮件报告」](../server/README.md#邮件报告)
- **隐私保护** — 不采集键盘输入、不截屏；应用上传仅含应用名和时长。主动开启网站邮件图表后，
  还会上传网站域名、每小时用量和使用起止时段，不含窗口标题、网页路径或搜索词。订阅邮箱不填就不发送

## 导入约定（改目录结构时必看）

`client/` 是一棵**导入树的根**。包内一律用「以自己这个根为起点」的绝对导入，
不写相对导入：

```python
from core.storage import record_fragment     # ✅
from system.icons import get_icon            # ✅
from ..core import storage                   # ❌ 不要用相对导入
import storage                               # ❌ 老写法，已失效
```

同一个根必须同时体现在两个地方，否则会出现「源码能跑、打包后找不到模块」：

- `client/main.py` 把 `client/` 插进 `sys.path`
- `client/app.spec` 的 `pathex=['client 目录']`

## 安装与运行

### 方式一：下载使用

本项目发行物以 [sowidy/PcTime Releases](https://github.com/sowidy/PcTime/releases) 为准。
如提供 Windows 压缩包，解压后运行 `PcTime.exe`，无需安装 Python 环境。

### 方式二：从源码运行

```bash
git clone https://github.com/sowidy/PcTime.git
cd PcTime
pip install -r client/requirements.txt
python client/main.py
```

（`.venv` 建在仓库根目录即可，`client/` 和 `server/` 都用它。）

### 方式三：自行打包

```bash
pip install -r client/requirements.txt
pip install pyinstaller

cd client
python tools/generate_icon.py
pyinstaller app.spec --clean
```

打包产物位于 `client/dist/PcTime/`。也可以直接双击 `client/build.bat`
一键完成（它会自动优先使用仓库根目录下的 `.venv`）。

> ⚠️ 改 `build.bat` 时请**只写英文注释**（保持纯 ASCII）。cmd.exe 是按系统的
> OEM 代码页（中文 Windows 上是 GBK）去读 .bat 文件的，不是 UTF-8，所以文件里
> 的中文会被解析成乱码并导致整个脚本报「不是内部或外部命令」。`chcp 65001`
> 只管控制台输出编码，救不了这个。其它 `.py` 文件不受影响，中文注释照常。

## 自动导出

程序在后台定期把使用时间导成 CSV，按「年 / 月 / 日」分层存放：

```
client/data/2026/10/14/daily_2026-10-14.csv              每日：当天各应用汇总
client/data/2026/10/12/weekly_2026-10-12_2026-10-18.csv  每周：整周各应用汇总
client/data/2026/10/01/monthly_2026-10.csv               每月：整月各应用汇总
```

（打包成 exe 运行时，这些文件改放到 `%APPDATA%\PcTime\data\` 下，
因为程序安装目录可能是只读的。数据库同理。）

文件里是各应用的使用时长明细（日期 / 应用名 / 显示名 / 使用时长 / 使用次数），
带 UTF-8 BOM，可直接用 Excel 打开而不乱码。

几点说明：

- **补导机制**：程序不是一直在后台跑，用户可能关几天再打开。程序会记住
  「上次导出到哪一天」，下次启动时把中间缺的那几天补齐，不会留空档。
- **幂等**：文件名只由周期决定（不含运行时间），重复导出只会覆盖同一个文件，
  所以「今天」的 CSV 每次都会被刷新成最新状态，不会越导越多。
- **手动触发**：设置页有「立即导出」按钮，托盘右键菜单也有「立即导出数据」。
- 可以在设置页关掉自动导出。

## 数据上传

客户端收集本机每天的「应用名 + 使用时长」，上传到自建服务端存储；服务端按
**设备** 区分数据（同一台机器换用户不影响归属）。这份数据用来生成报告邮件。

- **身份**：客户端首次运行生成一个 UUID（称为**设备 ID**）存在本地，之后一直沿用。
  它同时是读取自己数据的凭据 —— 服务端认它不认人。设置页可以查到并复制它。
- **节奏**：后台线程每小时醒来检查一次「有没有该传的」。真正决定传哪些天的是
  一条「水位线」加上最近 3 天的**回看窗口**：
  - 水位线记录传到哪天了，所以关了一周再开机会自动把中间缺的日子补上；
  - 最近 3 天每次都会重传，因为**今天的时长还在长**，只有反复刷新才不会丢数据。
    副作用是「服务端换了库、数据被清了」这种情况能自愈。
- **幂等**：服务端按「设备 + 日期」整块覆盖写入，所以重传同一天不会让时长翻倍。
  客户端断网后放心重试即可。
- **失败处理**：连不上 / 5xx / 429 会退避重试（2s→4s→8s，共 4 次）；4xx 直接
  放弃，因为那是「发的东西有问题」，重试多少次都一样。失败时水位线不动，
  下次从头再来。
- **手动触发**：设置页有「立即上传」「测试连接」按钮，托盘右键菜单也有
  「立即上传数据」。这两个入口都以 `force=True` 调用，所以**即使关掉了自动上传，
  手动点仍然会传**（用户主动发起的操作不该被开关挡住）。
- 网络请求全部由 `client/net/uploader.py` 发出，用的是标准库 `urllib`
  （客户端不想再引第三方 HTTP 库）。

> ⚠️ 改 `app.spec` 时注意：`excludes` 里**不能**有 `http` 和 `email`。
> `urllib.request` 会链式导入它们，排掉之后打包版一上传就报
> `ModuleNotFoundError: No module named 'http'`，而且源码模式跑得好好的，
> 只在打包版复现，很难查。

服务端那边长什么样见 [server/README.md](../server/README.md)。

## 客户端配置（.env）

服务端地址、超时、重试次数这些都能改，**不用改代码也不用重新打包** —— 写进
`.env` 就行（模板 `client/.env.example`）：

```ini
PCTIME_SERVER_HOST=127.0.0.1
PCTIME_SERVER_PORT=8000
```

取值顺序**先命中的赢**：真环境变量 → `.env` → 代码里的默认值。

`.env` 放哪：**先找程序旁边，找不到再退到 `%APPDATA%\PcTime\`**。

从旧版升级时不用手动搬数据库：若 `%APPDATA%\UsageTracker\usage.db` 存在且新目录尚无
`usage.db`，客户端仍使用整个旧目录（包括导出文件和旧 `.env`）。程序目录旁的 `.env`
始终优先。配置键推荐改为 `PCTIME_*`；已有 `USAGETIME_*` 仍可读，同名新键优先。
开机自启和浏览器扩展的旧标识也保留兼容。确认新版本正常运行前不要删除旧目录或旧程序。

| 你怎么跑 | 首选 | 兜底 |
| --- | --- | --- |
| 跑源码（`python client/main.py`） | `client/.env` | 同上（两个候选是同一个目录） |
| 打包版 exe | exe 旁边，也就是解压出来那一层 | `%APPDATA%\PcTime\.env`；旧数据未迁移时为 `%APPDATA%\UsageTracker\.env` |

**实际读的是哪一份，设置页「数据上传」那一块的「配置：」一行会写**，鼠标悬停能看到
完整路径。客户端没有日志文件，而两个候选位置意味着「明明改了却没生效」几乎总是
改错了那一份，所以这一行是刻意加的。打包时 `.env.example` 会跟着 exe 一起发出去 ——
想改配置，把它改名成 `.env` 就行，不用去猜有哪些配置项。

| 配置项 | 含义 | 默认 |
| --- | --- | --- |
| `PCTIME_SERVER_URL` | 完整根 URL，优先于 HOST/PORT；支持 HTTPS 和代理路径 | 未设置 |
| `PCTIME_SERVER_HOST` / `_PORT` | 兼容旧版 HTTP 服务端地址 | `127.0.0.1:8000` |
| `PCTIME_REQUEST_TIMEOUT` | 单次请求超时（秒） | `15` |
| `PCTIME_RETRY_COUNT` / `_BACKOFF` | 失败重试次数 / 退避基数（秒） | `3` / `2.0` |
| `PCTIME_UPLOAD_CHECK_INTERVAL` | 后台多久检查一次该不该上传（秒） | `3600` |
| `PCTIME_RESEND_RECENT_DAYS` | 每次顺带重传最近几天 | `3` |

接口路径（`/api/v1`）和客户端版本号**刻意不可配**：它们是协议和事实，不是某台机器的
环境差异，理由写在 `client/core/config.py` 的注释里。

三条要注意的：

- **没有 `.env` 是正常情况**，客户端照常跑。发出去的压缩包里不带 `.env`，
  只带 `.env.example` —— 客户端必须能在完全没有它的情况下工作。
- **改完要重启客户端**才生效（配置是导入期算一次的模块级常量）。
- **写坏的数值不会让程序起不来**：`PCTIME_SERVER_PORT=abc` 会退回默认值。
  打包版是 `console=False`，导入期抛异常的表现是「双击了没反应」，用户看不到任何
  原因，所以这里刻意吞掉了转换错误。

> `.env` 的解析器在客户端和服务端各有一份（`client/core/envfile.py` 和
> `server/config.py`）。这是**刻意复制的，不是漏抽公共模块** —— 理由是打包：客户端
> 要引用 `client/` 之外的目录就得改 `app.spec` 的 `pathex`，而那种错只在「重新打包
> 后的 exe」上才暴露，源码模式反而一切正常。代价靠 `tests/test_envfile.py` 的
> `TestParsersAgree` 兜住：它把同一批输入喂给两份实现、要求结果逐字相同。

## 订阅每日报告

「设置 → 数据上传」卡片底下有「每日报告邮件」一块：勾上、填邮箱、点「保存」。
保存成功后服务端会每天 00:03 发一封昨天的完整汇总到那个邮箱（平日是日报，
报告日为周日时是整周周报，见 [邮件报告](../server/README.md#邮件报告)）。

几个容易搞混的点：

- **订阅和上传是两个开关**，互不影响。上传开关管的是「数据要不要出本机」，
  订阅开关管的是「数据到了服务器之后要不要再发一封信」。关掉其中一个
  不会顺手改动另一个。
- **本地优先：服务端连不上也存得住。** 点「保存」时先把邮箱和开关写进本机，
  再去同步服务端。同步失败（断网、或者服务端还没这台设备的记录）**不算失败**，
  只是标一个「待同步」，下次上传成功时自动补上 —— 上传成功本身就说明服务端是通的。
  所以「装好先填邮箱、过几天才上传」这种自然顺序不会被挡住，服务端挂了也不影响你
  改自己的设置。待同步期间界面是**琥珀色**的，并且会写明「还没同步到服务端」，
  不会让你以为已经生效了。
- **邮箱是走单独一个接口**（`POST /api/v1/subscription/{设备ID}`），不是搭上传的便车。
  上传体里虽然也有 `email` 字段，但只在「已订阅」时才带上，作用是服务端库被清空时
  让订阅状态自愈，不是设置订阅的通道。
- **退订也要走那个接口**，因为上传接口永远不会把 `subscribed` 改回 0（那是为了
  退订之后不被每天的上传自动订回来）。所以退订同样会打「待同步」标记。
- **退订只关开关，邮箱留着**，方便手滑之后订回来不用重打。
- 想验证服务端那边到底配好没有，可以在设置页点「测试连接」，或者用服务端的
  管理接口 `POST /api/v1/admin/daily-mail?dry_run=1` 空跑一遍。
- 除了「上传数据」和「保存订阅」这两处，客户端**不会**发出任何网络请求，
  其余功能都不依赖服务端（见[根 README 的隐私声明](../README.md#隐私声明)）。

## 技术栈

- **UI 框架**: PySide6 (Qt for Python)
- **数据库**: SQLite (WAL 模式)
- **进程监控**: psutil + Win32 API (GetForegroundWindow)
- **空闲检测**: Win32 API (GetLastInputInfo)
- **图标提取**: Win32 IImageList + SHGetFileInfo
- **网络**: 标准库 `urllib`（没有引第三方 HTTP 库）
- **打包**: PyInstaller
